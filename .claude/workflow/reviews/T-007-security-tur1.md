### 1.2 403 vs 404 kararı (ADR-0010 madde 5) — architect'in gerekçesi **BAĞIMSIZ DOĞRULANDI**

Architect'in önermesi: "varlık oracle'ı üyelik yanıtından **önce** ve **kimlik gerektirmeden** açıktır." Kaynak okumasına güvenmeyip **kimliksiz** isteklerle ölçtüm (gerçek Postgres + gerçek HTTP, mount edilmiş uygulama):

| Girdi (oturum **YOK**)                              | Yanıt                      |
| --------------------------------------------------- | -------------------------- |
| `/trpc/tenant.current` + **var olan** kiracı slug'ı | **401** `UNAUTHENTICATED`  |
| `/trpc/tenant.current` + **var olmayan** slug       | **404** `TENANT_NOT_FOUND` |
| `/trpc/tenant.current` + kiracı başlığı yok         | **404** `TENANT_NOT_FOUND` |

→ **Önerme doğru.** Kimliksiz bir saldırgan 401/404 ayrımından "bu kiracı var mı" sorusunu **sıfır kimlik bilgisiyle** yanıtlıyor. Dolayısıyla üyelik reddinde 403 dönmek, saldırganın zaten elde edebildiğinin üzerine **hiçbir ek bit** koymuyor (403'ün söylediği "kiracı var **ve** üye değilsin"in iki bileşeni de bağımsız olarak elde edilebilir: varlık 401/404'ten, oturum geçerliliği herhangi bir başka uçtan). Architect **yanılmamış**; 403→404 değişimi hiçbir sızıntıyı kapatmaz, yalnızca PR #3'te duyurulmuş sözleşmeyi bozardı. **Bulgu değil.**

**§7 madde 12'nin korunan yarısı ölçüldü** (`trpc-cross-tenant.isolation.test.ts`, gerçek Postgres, yeşil): 403 gövdesi tenant A'nın **ve** tenant B'nin `id`/`slug`/`name` değerlerinden hiçbirini taşımıyor; aynı kontrol **başlıklarda** da yapılıyor; `tenantId` yalnızca log kaydında. Ayrıca ölçtüm: `session.me` (protectedProcedure, kiracı-kapsamlı **değil**) yabancı kiracı bağlamında çağrıldığında da **403** dönüyor ve kullanıcının kendi `userId`/`sessionId`'si gövdeye **hiç** girmiyor → `/trpc` yüzeyinin **tamamı** üyelik istiyor.

**Muafiyet lisansına dönüşmüş mü?** **Hayır.** ADR-0010 madde 5'in "İşlevsel kural (bağlayıcı — bu karar bir muafiyet lisansı değildir)" paragrafı girdiyle kimliklenen kiracı-kapsamlı kaynaklar (ürün, sipariş, medya, ayar) için madde 12'yi **tam olarak** bağlayıcı tutuyor ve istisnayı "host çözümünden gelen kiracının kendisi" ile sınırlıyor. v0.0.6'da girdi alan prosedür **yok** (ölçüldü: iki prosedürde `.input()` çağrısı 0) → istisna fiilen tek bir vakaya bağlı. **Tek eksik:** CLAUDE.md §7'de çapraz referans yok → `low` (dördüncü bulgu).

### 1.4 Batching kapalı — **GERÇEK BATCHED İSTEKLE DOĞRULANDI**

İki bağımsız seviyede ölçüldü.

**(a) Handler seviyesi** (`createTrpcRequestHandler()` + gerçek `Request`/`Response`):

```
URL: /trpc/session.me,tenant.current?batch=1&input={"0":{},"1":{}}
→ 400 {"error":{"code":-32600,"message":"errors.http.generic","data":{"code":"BAD_REQUEST",
   "httpStatus":400,"appError":{"code":"HTTP_EXCEPTION",…,"requestId":"unknown"}}}}

/trpc/session.me?batch=1&input={"0":{}}            → 400 BAD_REQUEST   (tekil-batch de reddedildi)
POST /trpc/session.me,tenant.current?batch=1       → 400 BAD_REQUEST
/trpc/session.me,tenant.current (batch param YOK)  → 404 NOT_FOUND
/trpc/session.me  (kontrol)                        → 200 {"result":{"data":{…}}}
```

**(b) Uçtan uca HTTP** (mount edilmiş Nest uygulaması, geçerli oturum + üye olunan kiracı):

```
GET /trpc/session.me,tenant.current?batch=1&input={"0":{},"1":{}}  → 400
  gövdede kiracı adı ("SEC Kiracı A") var mı : false
  gövdede userId var mı                       : false
POST aynı yol (Origin: http://localhost:3000) → 403 CROSS_SITE_REQUEST_REJECTED (SameOriginGuard daha önce kesti)
```

→ `allowBatching: false` **gerçekten yürürlükte**; batched istekte **hiçbir prosedür koşmuyor** ve hiçbir veri dönmüyor. İstemci tarafında `httpBatchLink` kullanımı 0 (`rg` + `create-trpc-client.ts:15` yalnızca `httpLink`). Değişmezlik sağlam.
