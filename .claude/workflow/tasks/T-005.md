## ROADMAP v0.0.13 — birebir

**Hedef:** Veritabanı seviyesinde çapraz tenant erişimi imkânsız olsun.
**Hedefin gerekçesi:** Uygulama katmanı hatası veri sızıntısına dönüşmesin.

**Kapsam:**

- [ ] Tüm tenant'a bağlı tablolarda `tenant_id NOT NULL` + indeks
- [ ] Her tenant'a bağlı tabloda `ENABLE ROW LEVEL SECURITY` **ve**
      `FORCE ROW LEVEL SECURITY` + `USING (tenant_id = current_setting('app.tenant_id')::text)`
      politikası; şema linter'ı ikisini **birlikte** arar, biri eksikse CI kırmızı
      _(T-001 security Tur 1 S3: tablo sahibi `FORCE` olmadan RLS'i atlar)_
- [ ] Tenant context kancası: `CreatePrismaClientOptions`'a **additive** alan +
      `withTenant(tenantId)`; her transaction başında **parametreli**
      `SET LOCAL app.tenant_id` (dize birleştirme **yasak**; `SET LOCAL` bilinçli seçim —
      transaction bitince düşer, bağlantı havuzundaki bağlantı sonraki tenant'a sızdırmaz)
- [ ] **Rol ayrımı** _(T-001 security K3 kararıyla güncellendi)_:
      `arkesoft_migrator` (shadow DB için `CREATEDB`, migration'ları çalıştırır) +
      `arkesoft_app` (`NOSUPERUSER`, `NOBYPASSRLS`, hiçbir tablonun **sahibi değil**,
      yalnızca `SELECT/INSERT/UPDATE/DELETE`); migration ve uygulama bağlantı dizeleri
      **ayrı** ortam değişkenleri
- [ ] `createTenantIsolationSuite()` test yardımcısı: iki tenant kurup her repository'de
      çapraz okuma/yazmayı dener
- [ ] Yeni tablo eklendiğinde RLS politikasını zorunlu kılan CI kontrolü (şema linter)

**Dokunulan paketler:** `packages/db`, `apps/api`

**Kabul kriteri:** `pnpm test:isolation` yeşil; RLS politikası olmayan tablo eklendiğinde
CI kırmızıya döner. Ek olarak **üç doğrulama sorgusu** geçmeli:

1. `select rolsuper, rolbypassrls from pg_roles where rolname = current_user` → `f | f`
2. `select relrowsecurity, relforcerowsecurity from pg_class where relname = 'tenant_membership'` → `t | t`
3. `app.tenant_id` ayarlanmamış oturumda `select * from tenant_membership` →
   **0 satır** (hata değil, boş sonuç)

### "Tüm tenant'a bağlı tablolar" = tek tablo değil, **mekanizma**

Bugün `TENANT_SCOPED_TABLES` tek eleman taşıyor (`tenant_membership`). Kapsam bu tabloyu
özel-durum yapmak **değil**; politika üretimi, linter ve izolasyon süitinin **taksonomi
dizisi üzerinden parametrik** olması. Ölçüsü **AC9**.

### İki ADR çatışması — architect bunları kapatmadan ilerlemesin

- **ADR-0003 madde 7:** _"Prisma `migrate dev` üretir; **elle SQL düzenlemesi yapılmaz**"_.
  Bu sürüm **zorunlu olarak** elle SQL getiriyor (politika, rol, `FORCE RLS`, `GRANT`).
  **ADR-0003 tadil edilmeli** (dar istisna: "RLS/rol/grant DDL'i elle yazılır") veya
  ADR-0007 istisnayı açıkça devralmalı. Yoksa `docs`/`solid` **ADR ihlali** yazar.
- **`DROP POLICY IF EXISTS` bu sürümde YASAK.** T-004 bekçisi harf duyarlı düz
  `includes('DROP ')` ile tarıyor (`migration-set.ts:234`). İdempotent politika yazımının
  yaygın deseni bekçiyi **kırmızıya düşürür** ve kapsam dışı bırakılan muafiyet
  mekanizmasını zorunlu kılar. Migration'lar bir kez koşar; idempotency gerekmez.
  **Kısıt: v0.0.13 migration SQL'i `DROP ` jetonu içermeyecek.**

### PM riskleri

1. **[architect'in çözmesi gereken] `FORCE RLS` + sahip rol → seed ve migration kırılır.**
   `FORCE RLS` tablo **sahibini de** RLS'e tabi kılar. Politika yalnızca `TO arkesoft_app`
   yazılırsa `arkesoft_migrator` (sahip) için **uygulanabilir politika kalmaz** →
   varsayılan ret → `db:seed`'in insert'i **başarısız**. **AC10 bunu zorunlu doğrular.**
2. **[ROADMAP'in lafzı yanlış] `SET LOCAL` parametre kabul etmez.**
   `SET LOCAL app.tenant_id = $1` PostgreSQL'de **geçersiz** — `SET` bağlanabilir
   parametre almaz. ROADMAP'in "parametreli `SET LOCAL`" ifadesini **ve** dize
   birleştirme yasağını aynı anda karşılamanın tek yolu
   **`set_config('app.tenant_id', $1, true)`**. Architect bunu ADR'de belgelemeli.
3. **262 testin bir kısmı kaçınılmaz değişecek.** `tenant_membership` okuyan testler
   `arkesoft_app` ile koşarsa context kurmadıkça **0 satır** görür. AC7 bunu
   "güncelleme" olarak izinli kılıyor, **gevşetme** olarak **değil** — `qa` test sayısı
   ve `skip` sayısını ölçmeli.
4. **CI Postgres servisi rol ayrımını desteklemeli.** `ci.yml` `services:` bugün tek rol
   kaldırıyor; `prepare-db` iki bağlantı dizesi + idempotent rol kurulumu öğrenmeli.
   **A-V21 (localhost allowlist) korunmalı.**
5. **`.env` geriye uyumluluğu.** `DATABASE_URL`'in **anlamı değişiyor** (artık
   migration/sahip rolü). Yeni değişken **zorunlu** yapılırsa kullanıcının mevcut `.env`'i
   `pnpm env:check`'te kırmızı verir — geçiş mesajı anlaşılır olmalı.
6. **Yıkıcı migration riski ölçüldü: YOK.** SQL'i `CREATE ROLE`/`GRANT`/`CREATE POLICY`/
   `ALTER TABLE … ENABLE|FORCE RLS`/`OWNER TO` içerir; `DROP COLUMN`, `TRUNCATE`,
   `NOT NULL` ekleme **yok** → §10.10 ihlali yok. Tek koşul `DROP POLICY IF EXISTS`
   yasağı. `OWNER TO`/`REVOKE` yıkıcı **değil** ama **geri alınabilir** olmalı —
   rollback yolu `docs/development.md`'de yazılı olsun.

## Architect Tasarımı

**VERSİYON ETKİSİ: `minor`** · Yeni ana bağımlılık **yok** · `major` **değil** →
kullanıcı onayı gerekmedi · **ADR-0007 yazılacak** + **ADR-0003 madde 7 tadil edilecek**
(taslak metinler architect raporunda, `docs` uygulayacak).

> **minor gerekçesi:** RLS + rol ayrımı + `withTenant()` + `test:isolation` yeni bir
> yetenek. `patch` **değil** (davranış sözleşmesi değişiyor: context'siz
> `tenant_membership` sorgusu artık **0 satır** döner). `major` **değil** — MAJOR tanımı
> _tenant'ın müdahalesi_ gerektiren değişikliktir; veri modeli göçü yok (şema değişmiyor),
> panel yok, API major'ı yok, üretimde tenant yok. **Operatöre dönük** kırılma var
> (`.env` + `db:bootstrap`) ama MAJOR tanımı tenant etkisine bakar.

### K-E1 — Linter **canlı Postgres kataloğunu** okur (V1 doğrulandı, kapsam açılmıyor)

Metin tarayıcısı **üç** şeyi yapısal olarak göremez: **(a)** `ALTER TABLE … ADD COLUMN
"tenant_id"` ile sonradan gelen kolon · **(b)** bir politikanın _uygulanabilir_ olup
olmadığı (`polroles`, `polwithcheck` NULL mı) · **(c)** `FORCE RLS`'in canlı durumu.
Ayrıca **AC2'nin üç sorgusu zaten katalog sorgusudur** ve AC3'ün probu canlı DB'de
geçici tablo kuruyor → metin tarayıcısıyla ikisi de **tanım gereği** karşılanamaz.

**T-004'ün metin bekçisi kaldırılmıyor, daraltılmıyor.** İki katman, **iki ayrı soru**:

| Katman                               | Soru                                                           | DB gerekir mi | Nerede                              |
| ------------------------------------ | -------------------------------------------------------------- | ------------- | ----------------------------------- |
| Metin bekçisi (`migration-set.ts`)   | Migration kümesi taksonomiyle tutarlı mı? Yıkıcı ifade var mı? | **Hayır**     | `pnpm test`, `guards`, AC12a        |
| Katalog linter'ı (`catalog-lint.ts`) | Canlı şema **gerçekten** izole mi?                             | **Evet**      | `pnpm test:isolation` (`api` hattı) |

→ **R-D1 bu sürümün hiçbir AC'sinin yolu üstünde değil → v0.0.14'te kalır.**

**Reddedilen:** yalnızca statik metin (üç kör nokta + kapsamı yeniden açar) · metin
bekçisini canlı linter'la **değiştirmek** (`.env`'siz prob ve `shared` hattı DB'siz) ·
`prisma migrate diff` ile drift (Prisma introspection RLS/politika/grant **görmez**).

### K-E2 — Politika `TO PUBLIC`; ayrım `GRANT`+sahiplikle; seed **uygulama rolüyle**

1. **Politikada `TO` yan tümcesi YOK.** `TO arkesoft_app` yazılırsa `arkesoft_migrator`
   (sahip, `FORCE RLS`'e tabi) için uygulanabilir politika kalmaz → varsayılan ret.
   `TO PUBLIC` ile **her iki rol de aynı kiracı yüklemine tabi**. Ek fayda: ileride
   eklenecek bir rapor/replika rolü **varsayılan olarak reddedilir**.
2. **Seed `arkesoft_app` ile koşar**, `tenant_membership` yazımını `withTenant()` içinde
   yapar → `db:seed` çalışma zamanı yolunu **egzersiz eder** (AC10 + AC2'nin "uygulama
   bağlantısıyla" şartı). Seed **iki transaction**: (1) platform tabloları (RLS yok),
   (2) `withTenant(tenant.id, …)`. Bölme **kaçınılmaz** — context'in girdisi 1. adımın
   çıktısı. Upsert'ler idempotent; **gerekçe yorumu `seed.ts` başına zorunlu**
   (CLAUDE.md §4'ten bilinçli sapma).
3. **Rol/sahiplik/grant DDL'i migration'a GİRMEZ.** Üç bağlayıcı sebep: roller **küme
   seviyesi** nesne · `CREATE ROLE` `CREATEROLE`/süper ister, migrator'da **yok** (V2) ·
   `prisma migrate dev`'in **shadow DB'sinde** migration kümesi yeniden koşar →
   `CREATE ROLE` "already exists" ile **patlar**. Aynı sebeple `OWNER TO` da girmez
   (dolu volume'da sahip `arkesoft`, migrator `ALTER` edemez — tavuk-yumurta).

| Katman           | Dosya                                                       | Kim koşar                   | İçerik                                                                                                                 |
| ---------------- | ----------------------------------------------------------- | --------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **Provisioning** | `packages/db/sql/bootstrap-roles.sql` + `pnpm db:bootstrap` | bootstrap süper kullanıcısı | `CREATE/ALTER ROLE`, sahiplik devri, `GRANT`, `ALTER DEFAULT PRIVILEGES`, `REVOKE CREATE ON SCHEMA public FROM PUBLIC` |
| **Migration**    | `<ts>_rls_tenant_isolation/migration.sql`                   | `arkesoft_migrator`         | **yalnızca** `ENABLE/FORCE RLS` + `CREATE POLICY`                                                                      |

**AC9 parametrikliği:** `ALTER DEFAULT PRIVILEGES FOR ROLE arkesoft_migrator … GRANT …
TO arkesoft_app` → yeni tablo için elle `GRANT` yazılmaz. Linter yine `has_table_privilege`
doğrular (bootstrap koşulmamışsa sessiz geçmez).

**Reddedilen:** migrator için **ikinci permissive politika** — PERMISSIVE politikalar
**OR**'lanır; `USING (true)` taşıyan ikincisi sahip rol için izolasyonu **tamamen kapatır**
ve o bağlantı dizesi aynı `.env`'de yaşıyor → _kolaylık kılığında izolasyon deliği_ ·
`BYPASSRLS` (V2 + §10.4) · seed'in migrator ile koşup `set_config`'i kendisi çağırması
(ikinci kod yolu → AC4'ün mekanik kontrolü pahalılaşır) · `/docker-entrypoint-initdb.d`
(dolu volume'da **hiç koşmaz**) · `REASSIGN OWNED BY` (paylaşılan nesneleri de kapsar).

### K-E3 — `set_config(…, true)` **ve** politika yüklemi `current_setting(…, true)`

**ROADMAP'in lafzında İKİ hata var:**

1. `SET LOCAL app.tenant_id = $1` **geçersiz** — `SET` bağlanabilir parametre almaz.
   → `set_config('app.tenant_id', $1, true)` (3. argüman `true` = `SET LOCAL` semantiği:
   transaction sonunda düşer, havuzdaki bağlantı sonraki kiracıya **sızdırmaz** —
   ROADMAP'in `SET LOCAL`'ı seçme **gerekçesi birebir korunur**).
2. **`current_setting('app.tenant_id')` tek argümanlı hâli, GUC ayarlanmamışsa
   `unrecognized configuration parameter` HATASI fırlatır** — oysa **AC2-3** açıkça
   _"0 satır (hata **değil**, boş sonuç)"_ istiyor. **ROADMAP kendi içinde çelişiyor.**
   → Yüklem **iki argümanlı** (`missing_ok = true`) yazılmak **zorunda**;
   `NULL` karşılaştırması `NULL` → satır filtrelenir, hata yok.
   Gereksiz `::text` cast'i **kaldırılır**.

**Migration SQL'i (bağlayıcı taslak):**

```sql
ALTER TABLE "tenant_membership" ENABLE ROW LEVEL SECURITY;
ALTER TABLE "tenant_membership" FORCE ROW LEVEL SECURITY;
CREATE POLICY "tenant_membership_tenant_isolation" ON "tenant_membership"
  USING ("tenant_id" = current_setting('app.tenant_id', true))
  WITH CHECK ("tenant_id" = current_setting('app.tenant_id', true));
```

`WITH CHECK` **açıkça** yazılır (varsayılan kopyalanmaya güvenilmez) ki linter
`polqual` **ve** `polwithcheck`'in ikisinin de NULL olmadığını iddia edebilsin.

**T-004 bekçisine karşı mekanik doğrulama:** `DROP ` eşleşmiyor · `SET NOT NULL`
eşleşmiyor · `CREATE_TABLE_TOKEN_PATTERN` 0 eşleşme → ayna bekçisi `0 > 0` false.
**Yorum satırlarında da `DROP ` yazılmayacak.**

### security · SONUÇ: PASS (0 kritik · 0 high · 2 medium · 5 low)

AGENT_BASELINE §4: 1–2 medium = PASS, bulgular teknik borca kaydedilir.

**Sürümün çekirdek iddiası canlı Postgres'te ampirik olarak TUTUYOR.** `arkesoft_app` ile
ölçülen birebir çıktılar:

```
current_user | rolsuper | rolbypassrls | rolcreatedb | rolcreaterole
arkesoft_app | f        | f            | f           | f

relname           | relrowsecurity | relforcerowsecurity
tenant_membership | t              | t

select count(*) from tenant_membership;   (app.tenant_id AYARLANMAMIŞ) → 0
```

Süper kullanıcıyla gerçek satır sayısı **1** → filtreleme gerçekten çalışıyor.
`arkesoft_migrator` (**sahip**) de **0 satır** görüyor → **`FORCE` fiilen etkili**.

Sahiplik ve ayrıcalık sınırı:

```
pg_tables where tableowner = current_user     → 0
pg_class'ta relowner = arkesoft_app           → 0 satır (tablo/sequence/tip dahil)
create table …                                → permission denied for schema public
create schema evil                            → permission denied for database
alter table … disable row level security      → must be owner of table
drop policy …                                 → must be owner of relation
```

`rolbypassrls=t` **yalnızca** bootstrap süper kullanıcısında (Postgres'in kaçınılmaz
özelliği; uygulama o rolle bağlanmıyor). `bootstrap-roles.sql:57-73` her koşuda
`NOSUPERUSER/NOBYPASSRLS/NOCREATEROLE`'a **yakınsıyor** → nitelikleri geri verecek yol yok.

Enjeksiyon **gerçekten denendi**:

```
set_config('app.tenant_id', $$x'; DROP TABLE "tenant_membership"; --$$, true)
  → 0 satır, sözdizimi hatası YOK, tablo HÂLÂ VAR
100.000 karakterlik tenantId → guc_len=100000, 0 satır, hata yok
BEGIN; set_config(…,true); COMMIT; current_setting(…, true) → boş (havuz sızıntısı KAPALI)
```

**Varlık oracle'ı kapalı** — üç `ROLLBACK`'li prob:

```
context=X, tenant_id=VAR OLAN yabancı tenant  → new row violates row-level security policy
context=X, tenant_id=VAR OLMAYAN tenant       → new row violates row-level security policy
```

**Ayırt edilemez** → RLS `WITH CHECK`'i FK trigger'ından **önce** değerlendiriyor.
