## İstek

ROADMAP v0.0.14 — **RBAC ve yetki modeli**, aşağıdaki alanlar `ROADMAP.md:700-722`'den
**değiştirilmeden** alınmıştır.

**Hedef:** Rol ve izin kontrolü tüm uçlarda uygulanabilir olsun.

**Devreden borç (T-006/v0.0.5, ADR-0008 "R-1 KARARI"):** parola hash'i/oturum belirteci/doğrulama
belirteci taşıyan üç tablo (`account`/`session`/`verification`) veritabanı seviyesinde (RLS)
**korunamıyor** — yapısal (giriş, asıldan önce hash'i okumak zorunda). v0.0.13 sonunda bu borç
"platform tablolarına RLS düşün" iken, v0.0.5 sonunda **üç tablo + üç kolon** büyüdü ve çözümün
şekli değişti: bu sürüm **`arkesoft_auth` rolü** + **kolon bazlı `GRANT`/`REVOKE`** +
`catalog-lint`'e **kolon yetkisi kural sınıfı** + **ikinci Prisma istemcisi/havuzu** + **üçüncü
zorunlu env** (ikinci operatör kırılması) teslim etmek zorunda.

**Kapsam:**

- [ ] Roller: `owner`, `admin`, `staff`, `support`, `readonly`; platform tarafında `platform_admin`
- [ ] İzin kataloğu (`product:write`, `order:read`, `theme:publish` ...), rol → izin eşlemesi
- [ ] `@RequirePermission()` dekoratörü ve tRPC `permissionProcedure`
- [ ] Davet akışı: e-posta ile üye davet, kabul, rol değiştirme, çıkarma
- [ ] Yetki değişikliklerinin denetim kaydına (audit log) yazılması
- [ ] `AuditLog` tablosu: actorId, tenantId, action, subject, diff, ip, userAgent

**Dokunulan paketler:** apps/api, packages/db, packages/trpc
**Kabul kriteri:** `readonly` rolü yazma ucuna 403 alır; davet akışı entegrasyon testi yeşil; izin
kataloğu ile dekoratör kullanımları arasındaki tutarlılığı doğrulayan test var.
**Bağımlılık:** v0.0.13, v0.0.5
**Tahmini büyüklük:** L

### ⚠⚠ İKİ YAPISAL ÇELİŞKİ — `pm`'in en değerli bulgusu

**Çelişki A — ADR-0008 "kolon bazlı REVOKE"yu DEĞERLENDİRİP REDDETTİ.** `0008:91` alternatifler
tablosu: *"`WHERE token = $1` gibi sorgular kolon için `SELECT` yetkisi ister → **giriş kırılır**.
Ayrıca `has_table_privilege(…,'SELECT')`'i `false` yapıp `APP_ROLE_MISSING_DML_PRIVILEGE` ile
**CI'ı kırar**."* ROADMAP ise **aynı ifadeyi** v0.0.14'ün teslimi diye yazıyor.
**Uzlaşma `0008:80`'de:** tablo bazlı REVOKE **`arkesoft_app`'ten**, kolon bazlı GRANT
**`arkesoft_auth`'a** → reddedilen şey *aynı rolde* kolon REVOKE'uydu, kabul edilen **rol ayrımı**.
⚠ **Ama CI kırılması AYNEN GEÇERLİ:** `catalog-lint.ts:419-430` REVOKE'un uygulandığı anda üç
tablo için bulgu üretir → **linter kural sınıfı teslimin ayağı değil, ÖN KOŞULU.**

**Çelişki B — `@RequirePermission()` dekoratörünün ÇAĞRI YERİ YOK.** Üretimdeki REST

### K-A5 · `permissionProcedure` + rol okuma kararı (ölçüm emri 1'in cevabı)

```ts
permissionProcedure(permission) → tenantProcedure.use(async ({ctx, next}) => {
```

üzerinden **her istekte** okunur. **Üç ölçülmüş gerekçe:**

2. **Guard bir ALS yazıcısı değildir.** Rolü oradan taşımak `RequestContext`'e **dördüncü** yazıcı (ve **ilk kez bir guard yazıcısı**) eklemek demekti; `AuthGuard` platformun **en çok denetlenmiş** güvenlik dosyası → bu sürümde **dokunulmuyor**.

### K-A11 · "Son `owner`" — INV-OWNER: her kiracının **TAM OLARAK BİR** `owner`'ı var

⚠ **"En az bir" yerine "tam bir" seçildi ve gerekçe MEKANİK, estetik değil:** *"en az bir"* klasik
**write-skew**'e açık (iki eşzamanlı owner çıkarma, her biri *"diğeri var"* görür) ve kapatmak
`SELECT … FOR UPDATE` ister → `TenantTransactionClient`'a `$queryRaw` eklemek gerekirdi, **oysa o
üye bilerek dışarıda** (`client.ts:201-203`). *"Tam bir"*de her işlem **tek owner satırını**
güncellemek zorunda → **satır kilidi işi serileştirir**, ek mekanizma **gerekmez**. Ürün tarafı
tutarlı (Shopify *"store owner"* emsali); gevşetme yönü (çoklu owner) **additive**.

**Zorlanma yeri: KODDA, CAS ile** (DB kısıtı **değil**):

```
updateMany({ where: { tenantId, userId: actorId, role: 'owner' }, data: { role: 'admin' } })
  → count === 0  ⇒  409   (artık owner değil / yarış kaybedildi)
update({ where: { tenantId_userId: {tenantId, userId: target} }, data: { role: 'owner' } })
writeAuditLog(member_role_changed) × 2     // AC7'nin "iki adım"ı = TEK transaction'da iki satır
```

Ayrı `member.transferOwnership` prosedürü **yok** — devir, `updateRole({userId, role:'owner'})`'ın
owner tarafından çağrılmasıdır.

**Reddedilen DB mekanizmaları (hepsi ölçüldü):**

| Mekanizma | Red gerekçesi |
| --------- | ------------- |
| Kısmi `UNIQUE INDEX … WHERE role='owner'` | Prisma şeması kısmi indeks **ifade edemez** → `migrate` drift yüzeyi; *"en fazla bir"*i verir, *"en az bir"*i **vermez** |
| `BEFORE DELETE` trigger'ı | ⚠⚠ `tenant_membership` **FORCE RLS** → trigger'ın sorgusu GUC yokken **her zaman 0 satır** görür (**ölçüm disiplini tuzak 1**) → **SESSİZCE İZİN VERİR**. `BYPASSRLS`/`SECURITY DEFINER` ile aşmak **§10 md 4 ihlali** |
| `Tenant.ownerUserId` + `ON DELETE RESTRICT` | Sahiplik için **ikinci doğruluk kaynağı**; backfill'i `tenant_membership`'i okumak zorunda ve **aynı FORCE-RLS körlüğüne** düşer |
